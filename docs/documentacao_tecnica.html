1Visão geral e objetivos

O SIRS automatiza o processo de recrutamento e seleção através de uma pipeline de avaliação em camadas, combinando análise semântica de currículos com extração de features estruturais baseada em regras. O sistema não substitui a decisão humana — ele ordena e pontua candidatos para que o RH concentre esforço nos perfis mais alinhados à vaga.

Problema resolvido

Triagem manual de currículos em volume — lenta, subjetiva e propensa a inconsistências. Com 50+ candidatos por vaga, o RH não consegue analisar todos com a mesma profundidade.

Abordagem adotada

Similaridade semântica vetorial (sem datasets rotulados) + sinais estruturais baseados em regras + análise de mercado em tempo real como proxy de relevância.

Três camadas de avaliação

1. Score curricular automático (bi-encoder + bônus)
2. Entrevistas com score 0–10
3. Score consolidado ponderado

Pesos configuráveis

Cada vaga define seus próprios pesos para requisitos vs. mercado, e para currículo vs. entrevistas. O sistema se adapta ao perfil de cada processo seletivo.

Vetores pgvector

A extensão pgvector adiciona o tipo vector(N) ao PostgreSQL, permitindo armazenar e comparar embeddings diretamente no banco. O sistema usa 384 dimensões (configurável via EMBEDDING_DIM).

CampoO que representaQuando é None
curriculos.vetor_embeddingCV completo vetorizadoAntes do processamento
curriculos.vetor_secao_expSeção Experiência do CVSeção não detectada no CV
curriculos.vetor_secao_skillsSeção Habilidades do CVSeção não detectada no CV
vagas.vetor_vagaRequisitos da vaga vetorizadosNunca (criado junto com a vaga)
vagas.vetor_mercadoSkills de mercado vetorizadasAntes de "Analisar mercado" ser acionado
Por que vetorizar seções separadas? O CV de um sênior tem muito texto. Comparar o vetor completo com o vetor da vaga dilui a parte relevante (experiência técnica) com ruído (objetivos, hobbies). Vetorizar a seção Experiência isoladamente e dar peso maior (60%) melhora a precisão sem precisar de um modelo diferente.

4Pipeline de IA — detalhado

O processamento de cada currículo passa por 7 etapas sequenciais. As etapas 1–3 são de transformação de dados; 4–7 são de scoring e explicação.

Etapa 1 — Extração de texto do PDF

Módulo: resume_parser.extrair_texto_pdf() usando PyMuPDF (fitz).

O PDF é percorrido página a página. Cada página que contém texto extraível é convertida em string. PDFs escaneados (imagens) não são suportados e geram exceção ValueError.

doc = fitz.open(caminho_pdf)
partes = [p.get_text("text") for p in doc if p.get_text("text").strip()]
texto = "\n".join(partes)

Etapa 2 — Segmentação em seções

Módulo: section_extractor.extrair_secoes()

O texto do CV é dividido em quatro seções temáticas: experiencia, habilidades, educacao, resumo. A segmentação usa dois mecanismos em sequência:

Estratégia 1 — Detecção por cabeçalho

Varre as linhas do CV procurando por padrões de cabeçalho (linhas curtas ≤60 chars, maiúsculas, ou que batem com regex conhecidas). Exemplos detectados:

Padrão detectadoSeção atribuída
EXPERIÊNCIA PROFISSIONAL, work experienceexperiencia
HABILIDADES TÉCNICAS, skills, stack tecnológicohabilidades
FORMAÇÃO ACADÊMICA, educationeducacao
RESUMO PROFISSIONAL, perfil, objetivoresumo

Estratégia 2 — Fallback por densidade semântica

Para seções não encontradas por cabeçalho, divide o texto em parágrafos e atribui cada um à seção com maior densidade de palavras-chave características. Por exemplo, um parágrafo com muitos nomes de tecnologias vai para habilidades.

Impacto no score CVs com cabeçalhos explícitos recebem scoring mais preciso — o vetor da seção Experiência representa diretamente o histórico profissional, sem misturar com formação ou hobbies. CVs sem cabeçalhos usam o vetor completo como fallback (menor precisão, mesma fórmula).

Etapa 3 — Vetorização (bi-encoder)

Módulo: resume_parser.vetorizar_texto()

Modelo: paraphrase-multilingual-MiniLM-L12-v2 — multilingual (PT/EN/ES/etc.), 384 dimensões, carregado em memória no primeiro uso (lazy load).

Cada texto (CV completo, seção experiência, seção habilidades, requisitos da vaga) é transformado em um vetor de 384 números reais com norma 1 (normalize_embeddings=True). A similaridade entre dois textos é calculada pelo produto escalar dos vetores, que com vetores normalizados equivale ao cosseno.

sim(a, b) = a · b = Σ(aᵢ × bᵢ) ∈ [−1, 1]

A escolha do modelo multilingual é deliberada: CVs brasileiros misturam português e inglês técnico ("desenvolvi APIs em Python para processamento de NLP"). Um modelo exclusivamente em inglês perderia contexto em português; um exclusivamente em português não captaria os termos técnicos. O multilingual captura ambos.

Etapa 4 — Extração de features estruturais

Módulo: feature_extractor

O embedding capta semântica mas ignora fatos estruturais: dois CVs com textos parecidos mas 2 vs 15 anos de experiência terão vetores próximos. O feature extractor usa regex e heurísticas para extrair sinais que o modelo ignora.

4.1 — Anos de experiência

Três estratégias em ordem de prioridade:

#EstratégiaExemploResultado
1Declaração explícita"12 anos de experiência em ciência de dados"12.0
2Soma de intervalos detectados2015–2019 + 2019–2023 (sem sobreposição)8.0
3Fallback conservadorMenor ano no texto: 2017 → span/1.4estimativa

Intervalos sobrepostos são mergeados antes de somar: [(2015,2019),(2017,2022)] → [(2015,2022)] = 7 anos, não 9.

Datas de formação acadêmica são excluídas quando a seção de experiência é detectada — evita contar anos de faculdade como experiência profissional.

4.2 — Nível de senioridade

Detecta o maior nível encontrado no texto:

NívelKeywords detectadasAnos típicos (fallback)
0 — Estágio/Traineeestagiário, trainee, aprendiz0
1 — Júniorjúnior, junior1
2 — Plenopleno3
3 — Sêniorsênior, senior, especialista6
4 — Lead/Stafftech lead, lead, staff, arquiteto9
5 — Gestãohead, coordenador, gerente12
6 — Direçãodiretor, vp, cto15

4.3 — Skills técnicas

Catálogo de 100+ skills canônicas (linguagens, frameworks, bancos de dados, cloud, DevOps, ferramentas de negócio, metodologias). Aliases normalizam variações: k8s → kubernetes, next.js → nextjs, devops → ci/cd, spring boot → springboot.

A detecção usa word-boundaries customizados que incluem pontos — necessário para detectar node.js sem fazer falso positivo com substrings.

4.4 — Proficiência por skill

Para cada skill detectada, analisa uma janela de ±70 caracteres ao redor da menção:

ModificadoresPesoExemplo
básico, iniciante, noções, beginner0.3"Python básico para scripts"
(sem modificador)1.0"Experiência com Python"
avançado, expert, sólido, domínio1.3"Python avançado, 8 anos"
Limitação conhecida A janela de ±70 chars pode "sangrar" entre skills próximas no texto. "Python avançado, Docker básico" pode fazer Python receber peso 0.3 (o "básico" do Docker entra na janela do Python). Para evitar isso, as skills devem estar separadas por mais de 70 chars, o que normalmente acontece em CVs bem estruturados.

Etapa 5 — Scores semânticos

Módulo: matching_engine

Score RH (aderência à vaga)

Com seção de experiência detectada: score_rh = 0.60 × sim(vetor_secao_exp, vetor_vaga) + 0.40 × sim(vetor_embedding, vetor_vaga) Sem seção (fallback): score_rh = sim(vetor_embedding, vetor_vaga)

Score Mercado (aderência ao mercado)

Com seção de habilidades detectada: score_mercado = 0.60 × sim(vetor_secao_skills, vetor_mercado) + 0.40 × sim(vetor_embedding, vetor_mercado) Sem seção: score_mercado = sim(vetor_embedding, vetor_mercado)

O vetor_mercado é gerado pelo Market Analyzer e representa as skills mais demandadas no mercado para o cargo daquela vaga. Se ainda não foi calculado, usa o próprio vetor_vaga como fallback.

Etapa 6 — Bônus estrutural

Módulo: feature_extractor.calcular_bonus_estrutural()

O bônus compensa limitações do embedding — dois CVs semanticamente similares mas com perfis estruturais muito diferentes (um sênior e um estagiário) receberão pontuações diferentes graças a este componente.

Ordem de cálculo importa O overlap de skills é calculado antes dos outros dois componentes porque condiciona o bônus de experiência — experiência em área irrelevante (0 overlap de skills) não deve ser premiada.

Componente 1 — Skills overlap (calculado primeiro)

skills_comuns = habilidades_cv ∩ habilidades_vaga SE skills_comuns = ∅ E habilidades_vaga ≠ ∅: bonus -= 0.15 ← penalidade por irrelevância completa SE skills_comuns ≠ ∅: peso_total = Σ proficiência(skill) para cada skill em skills_comuns overlap = peso_total / |habilidades_vaga| bonus += overlap × 0.08 ← max +0.08 com overlap=1 e prof=1

Componente 2 — Experiência (escalada pelo overlap)

ratio = anos_candidato / anos_requeridos_vaga escala = max(overlap, 0.3) ← experiência irrelevante vale ≥30% menos SE ratio ≥ 1.0: bonus += 0.08 × escala ← cumpre/supera SE ratio ≥ 0.7: bonus += 0.03 × escala ← próximo do requisito SE ratio < 0.35: bonus -= 0.10 ← muito aquém (não escalado)

Componente 3 — Senioridade

diff = nivel_candidato − nivel_requerido_vaga diff == 0: bonus += 0.07 ← nível exato diff == 1: bonus += 0.03 ← um nível acima (ok) diff > 1: bonus -= 0.01 ← overqualification diff == -1: bonus -= 0.05 ← um nível abaixo diff == -2: bonus -= 0.10 ← dois níveis abaixo diff ≤ -3: bonus -= 0.15 ← mismatch severo bonus = clamp(bonus, -0.25, +0.25)

Etapa 7 — Score final e explicação XAI

Módulo: matching_engine.calcular_score_curriculo() e gerar_explicacao()

score_curriculo = clamp( score_rh × peso_rh + score_mercado × peso_mercado + bonus_estrutural, 0.0, 1.0 ) × 100

O bônus é aplicado ao score combinado (não apenas ao score_rh), garantindo que os sinais estruturais influenciem o resultado independentemente dos pesos configurados na vaga.

A explicação XAI é gerada junto e salva em curriculo.explicacao. Ela mostra ao RH:

  • Contribuição em pontos de cada componente
  • Classificação semântica: excelente (≥80%), bom (≥65%), regular (≥50%), baixo
  • Skills detectadas no CV em comum com a vaga
  • Anos de experiência e nível de senioridade extraídos

Reranking por cross-encoder (sob demanda)

Módulo: reranker.py — modelo BAAI/bge-reranker-base

O bi-encoder gera vetores isolados para cada texto — rápido, mas perde interações entre os dois textos. O cross-encoder lê o par (requisitos_vaga, trecho_cv) juntos em uma única passagem pelo modelo, capturando relações cruzadas.

Bi-encoderCross-encoder
Como funcionaVetoriza cada texto independentemente; compara por produto escalarLê os dois textos juntos no mesmo forward pass
ComplexidadeO(1) na leitura (vetor já salvo)O(N) — processa cada par na chamada
PrecisãoBoa para retrieval em escalaMais preciso para reranking de top-N
Quando usarOrdenação automática de todos os candidatosRefinamento dos top-20 sob demanda

O modelo é carregado em memória apenas na primeira chamada (lazy load, ~270 MB). O endpoint POST /vagas/{id}/rerankar processa os top-N candidatos e retorna a lista reordenada com score_rerank.

Market Analyzer

Módulo: market_analyzer.py — acionado via POST /vagas/{id}/analisar-mercado

Detecta a categoria do cargo (tech, direito, RH, engenharia, financeiro, marketing, saúde) e coleta dados de vagas reais:

CategoriaFonte de dadosFallback
techKaggle LinkedIn Jobs (~120k vagas)Skills curadas hardcoded
demaisAdzuna API (vagas em PT-BR)Skills curadas hardcoded

Sobre os textos coletados aplica TF-IDF para extrair as skills mais discriminativas do cargo. Depois vetoriza a lista ponderada de skills e salva como vaga.vetor_mercado. O score_mercado mede o quanto o CV do candidato está alinhado a essas tendências de mercado.

6Sistema de autenticação e autorização

JWT — JSON Web Tokens

O token JWT é gerado no login e deve ser enviado no header Authorization: Bearer <token> em todas as requisições protegidas. O payload contém sub (email), papel e exp (expiração). Duração padrão: 8 horas.

RBAC — controle por papel

Três papéis com acesso progressivo:

PapelO que pode fazer
RHCriar vagas, triagem, upload de currículos, agendar entrevista RH, tomar decisão final
GestorVer candidatos das suas vagas, agendar entrevista técnica, registrar resultado técnico, tomar decisão final
AdminTudo — mais gerenciar usuários e acessar auditoria completa

Controle por vaga — rhs_autorizados

Além do papel, existe controle granular por vaga. Quando um RH cria uma vaga, torna-se o criador exclusivo. Outros RHs não veem a vaga até serem adicionados à lista rhs_autorizados. O criador não pode remover a si mesmo.

Vagas criadas por Admin não têm rhs_autorizados (NULL = acesso aberto a qualquer RH).

Token de reset de senha — single-use

O token de reset tem TTL de 1 hora (via campo exp do JWT). Além disso, é garantido uso único através de um fingerprint do hash atual da senha:

No envio: fph = sha256(usuario.senha_hash)[:16] token = JWT { sub, tipo:"reset", fph, exp } Na verificação: payload = jwt.decode(token) SE payload["fph"] ≠ sha256(usuario.senha_hash)[:16]: → HTTP 400 "Token já utilizado" SENÃO: → troca a senha (senha_hash muda → fph antigo inválido)

Isso elimina a necessidade de banco de tokens revogados — a troca da senha invalida automaticamente qualquer token anterior.

7Pipeline de status das candidaturas

A candidatura percorre uma máquina de estados finita. Transições inválidas retornam HTTP 400. Cada transição é registrada em candidatura.historico.

NOVO └→ AGUARDANDO_PROCESSAMENTO (upload de CV) └→ PROCESSANDO_CURRICULO (Celery inicia) └→ TRIAGEM_PENDENTE (score calculado) ├→ APROVADO_TRIAGEM → ENTREVISTA_RH_AGENDADA │ └→ ENTREVISTA_RH_REALIZADA │ ├→ REPROVADO_RH → BANCO_TALENTOS │ └→ ENTREVISTA_TEC_AGENDADA │ └→ ENTREVISTA_TEC_REALIZADA │ ├→ REPROVADO_TECNICO → BANCO_TALENTOS │ └→ DECISAO_PENDENTE │ ├→ CONTRATADO │ ├→ NAO_APROVADO │ └→ BANCO_TALENTOS ├→ REPROVADO_TRIAGEM → BANCO_TALENTOS └→ BANCO_TALENTOS

9Webhook de importação

Endpoint: POST /webhook/importar — aceita application/json ou application/xml.

Autenticação

Header X-Webhook-Key: <valor>. Se WEBHOOK_SECRET_KEY não estiver configurado no .env, o endpoint é aberto (adequado para desenvolvimento). Em produção deve ser configurado.

Operações por entidade

EntidadeComportamento
vagasBusca por nome — cria se não existir, ignora se já existir. Dispara atualizar_mercado_vaga async.
candidatosUpsert por e-mail — atualiza campos não-nulos se já existir. origem="externo", fonte=<fonte>.
candidaturasVincula por vaga_external_id ou vaga_nome. Não duplica.
curriculo_textoCria Curriculo e dispara processar_curriculo_texto (Celery) para vetorizar sem PDF.

Isolamento de falhas

Cada candidato é processado dentro de um savepoint (db.begin_nested()). Um erro individual (e-mail inválido, vaga não encontrada) faz rollback só daquele registro — os demais continuam. O erro é reportado na lista erros da resposta junto com o id do registro afetado.

11Testes

O sistema usa pytest com um banco PostgreSQL dedicado (sirs_test_db). Cada teste roda dentro de um savepoint — ao final, o savepoint é desfeito e o banco volta ao estado anterior. Testes de API não interferem no banco de desenvolvimento.

Mocks automáticos (conftest.py)

  • mock_celery_tasks — impede que tarefas Celery sejam despachadas para o broker real
  • mock_vetorizar — retorna vetor fixo [0.1 × 384] em vez de carregar o modelo de embedding
  • mock_rate_limit — desativa o rate limiter baseado em Redis

Isso torna os testes de API muito rápidos (sem I/O de modelo). Para testar o pipeline de IA real, usa-se @pytest.mark.slow.

Testes de IA com embedding real

Os testes marcados com @pytest.mark.slow carregam o modelo real e verificam propriedades do sistema de scoring:

  • Ordenação semântica: candidato ideal > candidato mediano > candidato irrelevante
  • Especialização: data scientist pontua mais em vaga de DS do que desenvolvedor Python
  • Score final > limiar mínimo para candidatos adequados
  • Bônus estrutural favorece candidatos com experiência e skills alinhadas
# Rodar testes rápidos (sem modelo)
docker compose exec api pytest tests/ -v

# Testes com embedding real
docker compose exec api pytest tests/test_ai_curriculo.py tests/test_novos_curriculos.py -m slow -s -v

# Relatório detalhado de scoring
docker compose exec api pytest tests/test_novos_curriculos.py::TestPipelineNovos::test_relatorio_completo -m slow -s
