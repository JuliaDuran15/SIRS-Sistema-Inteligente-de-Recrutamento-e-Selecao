Celery é uma biblioteca Python que gerencia execução de tarefas em background. Ele tem três partes:
1. A tarefa — uma função Python normal decorada com @celery_app.task. Você define o que deve ser executado.
2. O broker — onde as tarefas ficam na fila esperando ser executadas. No SIRS é o Redis. A API coloca tarefas aqui, o worker busca daqui.
3. O worker — um processo separado que fica rodando em loop, buscando tarefas no broker e executando. No Docker Compose é o serviço worker.
O Celery é o carteiro do SIRS — a API escreve uma carta (tarefa) e joga na caixa de correio (Redis). O worker fica vigiando a caixa, pega a carta e entrega (processa). A API não precisa esperar a entrega para continuar trabalhando.

O que o Resume Parser precisa fazer
PDF enviado pelo candidato
        ↓
PyMuPDF — extrai o texto bruto do PDF
        ↓
spaCy — identifica entidades no texto (tecnologias, cargos, instituições)
        ↓
sentence-transformers — vetoriza o texto completo (384 dimensões)
        ↓
Normalização semântica — compara entidades encontradas com catálogo de skills
        ↓
Salva no banco: texto, vetor, skills extraídas

PyMuPDF (importado como fitz) lê arquivos PDF e extrai o texto. Um PDF por dentro é uma coleção de páginas, cada uma com objetos de texto posicionados em coordenadas. O PyMuPDF percorre esses objetos e devolve o texto como string.
Para o SIRS você vai usar "text" — o texto puro é suficiente para o NLP.

O spaCy é uma biblioteca de NLP (Processamento de Linguagem Natural). Ele recebe um texto e retorna um objeto rico com tokens, entidades, dependências gramaticais e muito mais.
Para o SIRS o mais importante é o NER — Named Entity Recognition (Reconhecimento de Entidades Nomeadas). O NER identifica automaticamente partes do texto que são entidades — nomes de pessoas, organizações, locais, datas.

A biblioteca sentence-transformers é um wrapper sobre modelos BERT que facilita a geração de embeddings. Você passa um texto, ela devolve um vetor numpy.
O modelo all-MiniLM-L6-v2 foi treinado com aprendizado contrastivo — dado um par de frases similares ele aproxima os vetores, dado um par diferente ele afasta. O resultado é que frases com significado parecido ficam próximas no espaço vetorial.

Três schemas, cada um com responsabilidade clara:
VagaCreate — usado no POST /vagas. O analista preenche o nome e os requisitos em texto livre. Os pesos têm valores padrão mas podem ser ajustados. Valida que os pesos somam 1.0.
VagaResponse — o que a API devolve em qualquer endpoint de vaga. Não expõe o vetor_vaga (lista de 384 floats) porque poluiria a resposta sem utilidade para o frontend.
VagaUpdatePesos — usado no PATCH /vagas/{id}/pesos. Só os pesos, sem mexer em mais nada. Valida a soma também.
VagaUpdateRequisitos — usado no PATCH /vagas/{id}/requisitos. Só o texto, e o endpoint recalcula o vetor automaticamente.

Por que botão manual em vez de automático?
Três razões:

1. Custo computacional — só faz sentido quando o RH vai usar o ranking

Se reordenasse automaticamente ao carregar a página, rodaria o cross-encoder em toda visita, mesmo que o RH só queira checar o status de um candidato específico.

2. Transparência para o usuário

O RH precisa saber que a ordem mudou e por quê. Um reorder silencioso causaria confusão ("por que João estava em 1º e agora está em 5º?"). O botão sinaliza: "cliquei → o sistema reprocessou com IA mais precisa".

3. O bi-encoder já é bom — o cross-encoder é um refinamento

A lista bi-encoder + bônus estrutural já é uma boa ordenação. O cross-encoder corrige casos onde:

Dois candidatos têm scores parecidos mas um claramente encaixa melhor
O CV usa linguagem muito diferente da vaga mas o conteúdo é equivalente
Skills implícitas (alguém que trabalhou em "sistemas distribuídos" provavelmente conhece Kafka mesmo sem mencionar)
O botão deixa o reranking como um recurso consciente, não como ruído automático. O visual muda para "✓ Reordenado" para que o RH saiba que aquela lista foi refinada pelo cross-encoder.


Resumindo o fluxo completo:


1. Candidato envia CV
        ↓
2. Celery: bi-encoder vetoriza + score_rh calculado
   (rápido, automático, para todos os candidatos)
        ↓
3. VagaDetalhe: lista ordenada por score_curriculo
   (já inclui seções + bônus estrutural)
        ↓
4. RH clica "Reordenar (IA)"
        ↓
5. Cross-encoder processa top-20 pares (vaga, cv)
   (preciso, alguns segundos, sob demanda)
        ↓
6. Lista reordenada com score_rerank — candidatos
   com melhor fit semântico real ficam no topo


   O que cada modelo faz de verdade
Bi-encoder — gera um vetor que representa o significado do texto de forma isolada:


encode("Desenvolvedor Python 5 anos FastAPI") → [0.12, -0.34, 0.87, ...]
                                                       ↑
                                               384 números que representam
                                               o "sentido" desse texto
O vetor fica salvo. Você compara com o vetor da vaga a qualquer hora, sem precisar do CV original.

Cross-encoder — lê os dois textos juntos, como um humano leria:


encode("requisitos da vaga" + "[SEP]" + "texto do CV") → 0.87
Não gera vetor. Gera diretamente uma nota de compatibilidade. Não tem nada para armazenar — só faz sentido quando você tem os dois textos ao mesmo tempo e quer uma resposta binária: "quão compatíveis esses dois são?".

Por que não rodar no momento do upload
Se rodasse o cross-encoder no upload, teria que rodar de novo toda vez que a vaga mudar:

Evento	Bi-encoder	Cross-encoder
Novo CV enviado	Vetoriza o CV → salva. Compara com vetor da vaga → salva score	Roda (CV + vaga) → salva nota. OK até aqui
RH edita requisitos da vaga	Revectoriza a vaga → recalcula score para todos os CVs	Precisa rodar novamente para cada CV — não tem o que reutilizar
RH troca os pesos	Recalcula score com nova fórmula usando vetores já salvos	Precisa rodar novamente para cada CV
Ranking de mercado atualiza	Usa vetor_mercado já salvo	Precisa rodar novamente para cada CV
Com 200 candidatos e uma vaga que é editada 5 vezes, o bi-encoder roda 200 vezes no total. O cross-encoder rodaria 200 × 5 = 1000 vezes — cada uma levando ~0.15s na CPU, totalizando ~2.5 minutos de processamento extra por edição.

Quando o cross-encoder faz sentido como task automática
Tem um cenário onde vale rodar automaticamente: quando o conjunto de candidatos está estável (vaga fechou para novas inscrições) e o RH vai fazer a triagem em bloco. Poderia ser uma task agendada:


Vaga fecha → Celery roda cross-encoder para todos os candidatos
           → Salva score_rerank no banco
           → RH abre a vaga e já vê a lista re-rankeada
Mas isso exigiria uma nova coluna score_rerank na tabela candidaturas, lógica de quando disparar a task, e tratamento de vagas que reabrem. O botão manual é o meio-termo: precisão do cross-encoder sem o custo de manter tudo sincronizado.

IA e Scoring
Alta prioridade

Extração de skills via LLM — o feature_extractor.py atual usa regex. Não detecta "experiência com pipelines de dados em nuvem" como Spark/AWS, nem "construí sistemas de recomendação" como ML. Um prompt para Claude Haiku custaria ~$0.001/CV e eliminaria a necessidade de manter o dicionário de aliases manualmente.

Análise de trajetória de carreira — hoje só conta anos totais. Detectar progressão (estagiário 2016 → júnior 2018 → sênior 2022) é muito mais informativo que "6 anos de experiência" e permitiria comparar candidatos com mesma duração mas trajetórias diferentes.

Feedback loop — o sistema não aprende. Quando um candidato com score 45 é contratado e fica 3 anos, esse dado é desperdiçado. Uma tabela feedback_score com (candidatura_id, score, foi_contratado, meses_na_empresa) permitiria calibrar os pesos da fórmula com dados reais da empresa.

Requirement-level matching — atualmente compara CV inteiro vs. vaga inteira. O ideal seria: para cada requisito da vaga ("5+ anos Python", "experiência com Docker"), buscar evidência específica no CV. O cross-encoder bge-reranker-base já instalado faz isso, mas só no reranking manual.

Médio prazo

Modelo multilíngue — paraphrase-multilingual-MiniLM-L12-v2 captura melhor CVs em PT misturado com inglês técnico (padrão real no mercado BR)
HNSW index no pgvector — busca vetorial hoje é força bruta O(N). CREATE INDEX USING hnsw torna logarítmica, relevante com centenas de vagas e milhares de CVs
Score de viés — verificar se candidatos de certos grupos são sistematicamente penalizados pelo embedding (importante para compliance)


Dashboard analítico — os dados já existem no historico de cada candidatura: funil por etapa, tempo médio, histograma de scores, taxa de aprovação por vaga
Explicabilidade do score na UI — o gerar_explicacao() já calcula os componentes (experiência, senioridade, skills); só falta mostrar isso ao RH em vez de um número opaco
Comentários internos — thread por candidatura para RH e Gestor trocarem notas sem sair do sistema
Templates de vagas — reusar configurações (pesos, requisitos base) de vagas anteriores similares
Infraestrutura e Técnico
PDFs em storage persistente — atualmente ficam em /app/uploads dentro do container; se o container for recriado, somem. S3 ou volume Docker resolve
WebSocket para status do CV — hoje o frontend faz polling a cada 3s enquanto processa. WebSocket eliminaria esse custo e tornaria o feedback instantâneo

## Arquitetura

### Serviços (docker-compose)

| Serviço | Porta | Função |
|---|---|---|
| `api` | 8000 | FastAPI + Uvicorn, auto-migrações no boot |
| `worker` | — | Celery worker, processa CVs e mercado em background |
| `db` | 5432 | PostgreSQL 16 + pgvector (vetores 384d) |
| `redis` | 6379 | Broker + result backend do Celery |
| `frontend` | 3000 | React 18 + Vite, proxy `/api/*` → api:8000 |

### Pipeline de processamento de currículo

Quando um PDF é enviado ou texto chega via webhook:

1. **API** (`candidaturas.py`) salva o arquivo e dispara `processar_curriculo.delay()` via Celery
2. **Celery task** (`tasks.py`) chama:
   - `resume_parser.parsear_curriculo()` → extrai texto, gera `vetor_embedding` + `vetor_secao_exp` + `vetor_secao_skills`
   - `matching_engine.calcular_score_rh_multi_secao()` → `score_rh` (usa seções quando disponíveis)
   - `market_analyzer.obter_vetor_mercado()` → `score_mercado`
   - `feature_extractor.extrair_features_curriculo()` + `extrair_features_vaga()` → bônus estrutural
   - `matching_engine.gerar_explicacao()` → XAI salvo no `candidatura.historico`
3. Candidatura avança para `TRIAGEM_PENDENTE`

### Fórmula de scoring

```
score_rh (com seções):
  0.60 × sim(vetor_exp_section, vetor_vaga)
+ 0.40 × sim(vetor_cv_completo, vetor_vaga)
+ bonus_estrutural × 0.6

score_curriculo = clamp(score_rh × peso_rh + score_mercado × peso_mercado, 0, 1) × 100

score_total = (score_curriculo/100 × peso_curriculo)
            + (score_entrevista_rh/10 × peso_entrevista_rh)
            + (score_entrevista_tec/10 × peso_entrevista_tec)
```

`score_rerank` (cross-encoder, sob demanda) não é persistido — retornado só na resposta do endpoint.

### Máquina de estados das candidaturas

Transições válidas definidas em `candidaturas.py:TRANSICOES`. Cada transição é registrada em `candidatura.historico` (JSONB) com `{de, para, ator, em}`.

**Armadilha crítica do SQLAlchemy — mutação de JSONB:** Para que o SQLAlchemy detecte mudança num campo JSONB, é obrigatório criar um novo objeto list/dict:

```python
# ERRADO — SQLAlchemy não detecta a mudança, não persiste
historico = candidatura.historico or []
historico.append({...})
candidatura.historico = historico  # mesma referência

# CORRETO
historico = list(candidatura.historico or [])  # nova referência
historico.append({...})
candidatura.historico = historico
```

O mesmo vale para qualquer campo JSONB mutado in-place (`ranking_mercado`, `gestores_ids`, etc.).

### Controle de acesso (RBAC)

Três papéis: `RH`, `GESTOR`, `ADMIN`. Além do papel, vagas têm `rhs_autorizados` (lista de IDs). Um RH só gerencia vagas onde é criador ou está nessa lista; vagas criadas por admin são acessíveis a qualquer RH.

Guards reutilizáveis em `core/auth.py`: `QUALQUER_PAPEL`, `RH_OU_ADMIN`, `get_usuario_atual`.

### Módulos de IA (`backend/app/ai/`)

| Módulo | Responsabilidade |
|---|---|
| `resume_parser.py` | PDF → texto + vetores (embedding model singleton, lazy load) |
| `section_extractor.py` | Segmenta CV em seções; `texto_para_rerank()` para o cross-encoder |
| `feature_extractor.py` | Regex puro: anos (3 estratégias), senioridade, skills + proficiência, bônus ±0.25 |
| `matching_engine.py` | Calcula `score_rh`, `score_mercado`, `score_curriculo`, `score_total`, `gerar_explicacao()` |
| `market_analyzer.py` | Kaggle dataset + Adzuna API → vetor de mercado por cargo; filtro de EEO/benefits em `limpar_skills_desc()` |
| `reranker.py` | Cross-encoder `BAAI/bge-reranker-base` (~270MB), lazy load na 1ª chamada; normaliza logits via sigmoid |
| `tasks.py` | Tasks Celery: `processar_curriculo`, `processar_curriculo_texto`, `atualizar_mercado_vaga` |

**Armadilha — vetores numpy como booleanos:** Campos `vetor_embedding` e `vetor_vaga` são arrays numpy. Usar `if curriculo.vetor_embedding:` levanta `ValueError`. Sempre usar:
```python
if curriculo.vetor_embedding is not None and vaga.vetor_vaga is not None:
```

### Recálculo de scores

Quando pesos ou requisitos de uma vaga mudam, `_recalcular_scores_vaga()` em `vagas.py` recalcula `score_rh`, `score_mercado`, `score_curriculo` **e** `explicacao` para todos os currículos da vaga. É chamado automaticamente pelos endpoints `PATCH /vagas/{id}/pesos` e `PATCH /vagas/{id}/requisitos`.

### Frontend (`frontend/src/`)

SPA React com React Router. Navegar para a mesma rota não força remount — páginas com dados frescos (ex: Auditoria) devem ter botão de atualizar explícito ou `useEffect` com chave de navegação.

Componentes compartilhados em `components/`:
- `ExplicacaoScore.jsx` — breakdown de score (aderência, mercado, skills); usado em `VagaDetalhe` e `CandidatoDetalhe`
- `ComparacaoCandidatos.jsx` — modal de comparação lado a lado (2–3 candidatos)
- `Layout.jsx` — sidebar com link Auditoria visível apenas para admin

`api.js` centraliza todas as chamadas HTTP via axios com interceptor JWT.

### Webhook de importação

`POST /webhook/importar` aceita JSON ou XML. Autenticação via header `X-Webhook-Key` (opcional em dev, configurar `WEBHOOK_SECRET_KEY` em produção). Cada candidato roda em savepoint isolado — falhas individuais não cancelam a importação dos demais.
